description: Automatically turn abstract advice into a concrete artifact, demo, prototype, dataset, script, table, slide, prompt, or workflow that can be shown, tested, reused, or iterated. Use especially for client work, innovation, teaching, workshops, AI use cases, demos, and strategy.
keywords: [prototyping, demo moment, artifact-first, boundary objects, lean development, stakeholder alignment]
---

When the user's immediate task would benefit from something visible, e.g. when:

- The task involves clients, demos, workshops, use cases, pitches, teaching, assessments, proposals, strategy, AI adoption, data workflows, coding agents, or executive communication.
- The answer risks becoming abstract advice.
- The user is trying to persuade, teach, evaluate, operationalize, or decide.
- A small artifact would make the idea clearer: dataset, workbook, chart, script, HTML page, slide, rubric, prompt, checklist, before/after example, demo script, or test case.

Then, turn the idea into something the user can show, run, hand over, or test.

Prefer the smallest credible artifact that proves one point. Do not propose a platform when a table, prompt, script, or three-row example would do.

Rules:

- Solve the immediate task first. Add the artifact only if it makes the answer more useful.
- Start from the audience's felt problem, not the technology's capability.
- Find the demo moment: what should become obvious in under 30 seconds?
- Use real-enough inputs. Include mess, traps, ambiguity, missing fields, drift, exceptions, or objections when realism matters.
- Make the artifact reviewable. Show inputs, outputs, assumptions, success criteria, and limits.
- Prefer learning over polish. The first artifact should test the claim, not impress as production software.
- Preserve evidence. Good demos show their work: source snippets, confidence scores, test results, exception tables, lineage, or cited clauses.
- Design for reuse only after the artifact works once. Package as a template, prompt, workbook, repo, or workflow when there is clear repeat value.
- Avoid overbuilding. Production architecture is a later step unless the user asks for it.

When useful, add one compact note like:

```markdown
Artifact: <smallest useful thing>
Demo moment: <what the audience notices>
Success check: <how we know it worked>
Next step: <pilot/template/script/reuse path>
```

Skip this note when it would add clutter.

Durable basis: prototyping, lean validated learning, design thinking, demos as boundary objects, usability testing, and systems verification. Better agents can build faster, but humans still need concrete artifacts to align, test, trust, and decide.
